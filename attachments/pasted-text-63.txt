IMPLEMENTATION PROMPT — THE WEDDING CIRCLE: REAL-TIME CHAT VOICE SYSTEM

Implement a complete, production-oriented live voice chat feature inside my existing The Wedding Circle application. Replace the existing Music Track selector with a Mic control and add participant microphone-status indicators beside the existing Speaker control.

This is an implementation task, not a design proposal. Inspect the existing source code, make the necessary changes directly in the project, build the infrastructure in code, integrate the frontend with the backend, and test the actual behavior.

Do not stop after creating UI, mock buttons, placeholder APIs, or a demonstration.

1. Non-negotiable requirements

- Preserve the existing wedding Chat, messages, background images, themes, composer, plus button, Send button, profile button, filter, notifications, and bottom navigation.
- Remove the Music Track selection functionality from the Chat floating controls and replace it with live voice chat.
- Keep the existing Speaker button and its position.
- Add a new floating Mic button in the former Music Track button's position.
- Add a small arrow toggle and participant profile indicators immediately to the left of the Mic button.
- Both Mic and Speaker must initialize OFF for every participant on every fresh voice-chat session.
- Any authorized member of a wedding can participate in the voice conversation. Do not restrict it to hosts or co-hosts.
- Participants who enable their microphones must be able to talk to one another in real time. Participants who enable their speakers must be able to hear other participants.
- Participant indicators represent microphone-enabled status, not necessarily active speech.
- Implement the actual audio transport, signaling, authorization, real-time presence, and cleanup.
- Do not alter existing wedding data, authentication, membership roles, or unrelated features.

3. Define the microphone and speaker behavior correctly

Each participant has two independent local preferences:

- "micEnabled": whether their microphone is transmitting audio.
- "speakerEnabled": whether they hear remote participants.

Initial state:

- "micEnabled = false"
- "speakerEnabled = false"

These defaults must be enforced by the client and respected by the backend's session state. A new browser tab, fresh session, or new Chat entry must not automatically activate the microphone or speaker.

Behavior matrix

Mic| Speaker| Expected behavior
OFF| OFF| Cannot transmit or hear remote voice
ON| OFF| Can transmit voice; cannot hear others
OFF| ON| Cannot transmit voice; can hear others
ON| ON| Can transmit and hear other participants

If a user disables the Mic, immediately stop transmitting their microphone audio. Prefer stopping and releasing the microphone track when appropriate, rather than merely hiding the microphone icon.

If a user disables the Speaker, immediately mute all remote audio locally without disconnecting their microphone or changing other participants' states.

When a user leaves Chat, changes weddings, logs out, or ends their voice session, clean up the audio resources and stop publishing audio. Never leave the microphone transmitting in the background.

Use explicit button states and accessible labels. A muted icon alone is not sufficient feedback for permission failures, connecting, or connection errors.

4. Implement genuine group voice infrastructure

Inspect the complete existing application before selecting the architecture.

The current application uses a React 19, Vite, TypeScript, Tailwind CSS v4 and Express backend. Reuse the existing authentication, wedding membership, database, and real-time infrastructure wherever it is appropriate.

Do not introduce an unnecessary second database or replace the current authentication system.

Audio transport

Use a real-time audio architecture suitable for multiple simultaneous participants in the same wedding Chat.

Preferred approach:

1. If the project already has a configured and functional WebRTC SFU or managed group-audio provider, reuse it.
2. Otherwise, implement a proper WebRTC-based group-audio integration using an SFU such as LiveKit, or an equivalent production-capable service.
3. If the existing infrastructure is insufficient, add the required integration code, configuration, dependencies, server endpoints, event handling, and deployment documentation.

Do not build a simplistic peer-to-peer mesh and claim it is production-ready for large wedding groups. A mesh can require a separate peer connection for every other participant and scales poorly as the group grows.

The architecture must support multiple simultaneous speakers and listeners, with sensible bandwidth use and reconnect behavior.

Required audio behavior

- Publish microphone audio only when the user explicitly enables Mic.
- Subscribe to eligible participants' audio only when local Speaker is enabled.
- Mix/play multiple remote audio streams correctly.
- Avoid audio feedback and accidental microphone loopback.
- Handle browser autoplay restrictions by initiating audio playback from an appropriate user gesture and displaying a clear recovery action if playback is blocked.
- Request microphone access only when needed.
- Handle Bluetooth headsets and normal mobile audio-device changes as reliably as the browser APIs allow.
- Handle microphone permission denial, device removal, network interruptions, tab visibility changes, and browser refreshes.
- Never silently reactivate the microphone after a reconnect or page refresh.

Use secure transport: HTTPS in production and the secure WebRTC transport mechanisms supported by the chosen provider.

WebRTC signaling and credentials

Implement the actual server-side signaling or provider-token flow.

The backend must:

- Authenticate every signaling/token request.
- Verify the current user's membership in the requested wedding.
- Scope voice rooms to the correct wedding.
- Issue short-lived, appropriately scoped room credentials.
- Grant audio-publish permission only as authorized for that participant.
- Avoid granting room-admin privileges to ordinary participants.
- Never expose provider API secrets, signing keys, database credentials, or privileged service keys in browser code.
- Reject invalid wedding IDs, expired sessions, unauthorized participants, and forged identity claims.

If using LiveKit or another SFU, create a provider abstraction so the application can maintain its current UI and state model if the provider changes later.

Do not fabricate credentials or hardcode secret values. Add the required environment-variable references and deployment instructions. If external credentials or account setup are necessary, identify exactly what remains to be configured.

5. Backend, database, and real-time presence

Inspect the current database and real-time event system before designing new tables or collections.

Implement the smallest appropriate persistent or ephemeral state model needed for this feature. Reuse existing user and wedding identifiers rather than creating duplicate identities.

The model should represent, as appropriate:

- Wedding or voice-room ID.
- Authenticated participant ID.
- Microphone-enabled state.
- Voice-session connection status.
- Provider participant/session ID where needed.
- Server-generated join and heartbeat timestamps if needed.
- Session expiration and cleanup metadata.

Do not store raw audio recordings. This is a live conversation feature, not a recording feature.

Authoritative microphone status

The floating profile indicators must reflect the participant's actual server-authorized, active voice-session state.

A participant's profile must not appear merely because someone changed a local React state variable or forged a WebSocket event.

Use server-validated signaling and/or trusted provider participant events to update microphone status.

When the Mic is OFF, the profile must disappear from the active microphone list.

When the participant leaves, loses their session, or disconnects, clean up stale status after an appropriate timeout or authoritative disconnect event.

If a network interruption occurs, distinguish a temporary reconnect from a confirmed departure without leaving a stale profile visible indefinitely.

Real-time updates

Broadcast participant presence and microphone-state changes to authorized members of the same wedding only.

Use the existing real-time infrastructure if it supports this correctly. Otherwise, implement the minimum additional event transport required for reliable updates.

Use a consistent event contract for events such as:

- Participant joined voice.
- Participant microphone enabled.
- Participant microphone disabled.
- Participant disconnected.
- Participant reconnected.
- Participant left voice.

Validate all incoming events on the server. Do not trust client-supplied participant IDs or wedding IDs without verifying them against the authenticated session.

Make state changes idempotent so reconnects and duplicate events do not create duplicate participants.

If the project uses Supabase, Firebase, or another database, adapt this design to the actual configured provider. Do not assume a provider is working simply because its SDK is installed.

Persistence

Persist only what is necessary for reliable session management and debugging.

Microphone and speaker preferences should default OFF on each new voice session. Do not restore a previous ON state automatically.

If the user refreshes the page, the app must re-establish authentication and wedding membership, reconnect only after appropriate user action, and start with Mic and Speaker OFF.

Do not persist a raw audio stream or retain unnecessary voice-presence history.

6. Security, privacy, and authorization

Implement all of the following:

- Only authenticated users who are members of the selected wedding may enter that wedding's voice room.
- Use the existing trusted user ID and wedding membership records.
- Do not rely on display names, profile names, or client-supplied roles as proof of identity.
- Do not allow one wedding's participants to see or hear another wedding's participants.
- Prevent unauthorized publishing or subscribing through server-side checks and provider permissions.
- Validate token expiry and room membership when generating credentials.
- Apply appropriate rate limits to token issuance and signaling endpoints.
- Clean up sessions when authentication expires or a participant leaves.
- Do not expose private room credentials in logs, URLs, client error messages, or analytics.
- Use existing secure database access policies where applicable.
- Ensure a normal participant cannot modify another participant's microphone state.
- Do not add recording, transcription, or permanent audio storage.

The app must make it clear when the user has enabled their microphone. Do not activate the microphone without a deliberate user action.
