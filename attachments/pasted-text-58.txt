The Wedding Circle — Host Permissions Fix, Account Onboarding & Subscription Updates

Implement the following changes directly in my existing The Wedding Circle project. Inspect the current source code and data flow before editing.

Important: These are targeted fixes and product updates. Do not redesign the application, rebuild it from scratch, remove unrelated features, or overwrite existing wedding data.

1. CRITICAL: Fix Wedding Creator Incorrectly Identified as Guest

Current bug

When a user creates a wedding and enters it, the app identifies that same user as a Guest instead of the Host. Host Controls may appear in the More section, but the host settings and features are inaccessible or do not work correctly.

This issue must be fixed at its root.

Investigate and repair the complete identity and authorization flow

Trace the entire process:

1. User signs in or creates an account.
2. User creates a wedding.
3. The backend or existing data layer saves the wedding.
4. The creator is associated with that wedding.
5. The creator enters the wedding.
6. The app resolves their membership and role.
7. Host Controls and individual host actions are authorized.

Identify exactly where the creator's role becomes Guest, is incorrectly inferred, or fails to load.

Required behavior

- The authenticated account that successfully creates a wedding must automatically become its Host.
- Save the creator's stable account/user ID as the wedding's owner/creator ID.
- Create or update the corresponding wedding membership record with the Host role.
- Ensure that the ownership and membership records are consistent.
- Resolve the current user's role using their authenticated account ID and verified wedding membership, not their displayed name, editable host name, email text alone, or frontend-only state.
- Do not grant Host permissions merely because someone created a wedding-looking object on the client.
- Ensure the host identity is restored correctly after refresh, navigation, session restoration and re-entry into the wedding.
- Ensure the role is correct across Home, Chat, Live, Albums, More and every relevant host-management screen.
- Fix Host Controls so every feature that the Host is authorized to use actually opens, loads its settings, saves changes and persists those changes.
- Audit backend APIs, database queries, component conditions and permission checks for conflicting role definitions.
- Prevent guests from gaining host privileges by changing local state or editing a displayed name.
- Ensure co-hosts receive only their intended permissions and guests remain restricted.
- Do not accidentally change existing legitimate hosts into guests.

Existing wedding compatibility

Do not delete or recreate existing weddings to fix this.

For existing weddings, use a safe, documented reconciliation process. If the original creator can be verified from trusted ownership records, restore the correct Host membership. If ownership is ambiguous, flag the record for review rather than granting privileges to an arbitrary user.

Acceptance tests

Test at minimum:

- A newly registered user creates a wedding and immediately appears as Host.
- The same user can open and use all authorized Host Controls.
- Changes made in Host Controls persist after refreshing and re-entering the wedding.
- The creator remains Host after signing out and signing back in.
- A guest cannot access host-only APIs or settings.
- Editing a user's display name does not change their role.
- A co-host cannot use features reserved exclusively for the Host.
- Existing weddings and their data remain intact.

Do not mark this issue fixed merely by changing the visible role label. Both the displayed role and actual backend authorization must be correct.
