The Wedding Circle — Chat, Entry, Media, Background Sync & Live Screen Improvements

Implement the following changes in the existing The Wedding Circle application. These changes apply to mobile and desktop wherever relevant, while respecting the separate desktop and mobile layouts already established.

Before editing, inspect the existing components, database structure, authentication, guest entry flows, chat rendering, media preview, synchronization logic, live-stream state, and spectator chat transport. Make targeted changes to the existing implementation rather than rebuilding unrelated features.

1. Replace separate family and guest entry buttons

Remove the separate Enter as Family and Enter as Guest buttons from the wedding entry interface.

Replace them with one prominent primary button:

Enter Wedding Code

Requirements:

- Use one clear, visually prominent button consistent with The Wedding Circle's premium wedding design.
- Open the appropriate code-entry interface when selected.
- Accept every currently supported type of wedding access code, including family access codes, guest codes, and other existing valid wedding invitation/access codes.
- Automatically determine the appropriate entry flow from the supplied code.
- Preserve existing access validation, host/co-host permissions, membership rules, and privacy restrictions.
- Do not grant access simply because a code was entered. Validate the code against the existing server-side authorization rules.
- Display clear errors for invalid, expired, revoked, or unauthorized codes.
- Preserve existing valid codes and do not change their format unnecessarily.
- Do not delete or bypass any existing family or guest access functionality; consolidate its entry interface only.

Inspect the supplied screenshot. The shared photo appears inside a large rounded rectangular outline with empty space surrounding the actual image. The “Shared a photo” label also appears awkwardly positioned against the media and background.

Fix the underlying layout and styling rather than merely changing the border color.

- Ensure these changes work with all wedding themes and both light and dark modes.

Do not remove actual media, alter uploaded files, or break existing downloads.

12. Run background synchronization whenever the app opens

Whenever a user opens or reopens the application, initiate a background synchronization process so that available changes can be detected and retrieved.

Requirements:

- Trigger synchronization during app initialization or when the application returns to the foreground.
- Authenticate the current session before retrieving private wedding data.
- Identify the actual authoritative server source for each data category.
- Retrieve authorized updates for the current account and its wedding memberships.
- Synchronize eligible pending local changes safely.
- Detect new messages, wedding-setting updates, membership changes, invitations, and other supported wedding data changes.
- Refresh stale cached data when safe.
- Use stable IDs, versions, change tracking, or server timestamps as appropriate to the existing architecture.
- Avoid downloading every media file or retransferring the entire database on every app opening.
- Use incremental synchronization wherever supported.
- Use request deduplication, sensible retry backoff, and cancellation or coalescing of redundant sync operations.
- Do not block the user from opening the app while ordinary synchronization runs.
- Display an appropriate syncing or offline indicator only when useful.
- Preserve pending offline changes until the server confirms they have been processed.
- Detect conflicts rather than blindly overwriting newer server or local changes.
- Do not overwrite newer destination records or delete destination-only wedding data.
- Do not expose data belonging to another account or wedding.
- Keep the current Neon, Supabase, and Firebase architecture intact. Use the verified authoritative provider for each relevant service rather than assuming all data is in one database.
- Do not switch production routing or migrate databases as part of this feature.

If a sync fails, preserve local changes, report the error appropriately, and retry safely when connectivity returns.

15. Fix delayed and flickering spectator chat on the Live screen

Investigate and fix the existing live-session chat problems. These include:

- Spectator messages appearing on the live screen very late.
- Old chat messages repeatedly flickering or reappearing.
- New messages rendering inconsistently.
- Messages appearing out of order.
- The visible chat overlay behaving differently between live viewers.

Do not attempt to fix these symptoms solely by adding animation or forcing component re-renders. Inspect the actual message transport, event subscriptions, state updates, message identifiers, timestamps, cleanup behavior, and rendering logic.

Reliable message delivery

- Use the existing real-time transport wherever possible.
- Verify that the live host and spectators are subscribed to the correct live-session channel.
- Check for duplicate subscriptions after reconnects, screen changes, or live-session restarts.
- Clean up obsolete listeners when leaving a session or switching streams.
- Deduplicate incoming events using stable message IDs.
- Avoid repeatedly appending the same message when both an optimistic local event and a server event arrive.
- Handle connection interruptions and reconnects without replaying the entire chat overlay unnecessarily.
- Preserve message ordering using an authoritative timestamp or sequence number.
- Update UI state predictably rather than recreating the entire message list for every event.
- Keep the underlying persisted chat history unchanged unless the existing retention policy says otherwise.
- Separate the temporary live overlay from the permanent chat history so automatic overlay expiry does not delete actual messages.

Live chat overlay: one-minute lifetime

Show spectator messages and live-controller messages on the Live screen for 60 seconds from the time they are received by the live overlay, using a reliable timestamp policy.

Requirements:

- Newly received messages appear near the bottom of the live chat overlay.
- Older visible messages move upwards as newer messages arrive.
- Each message automatically disappears from the overlay after 60 seconds.
- Messages that expire must disappear from the live overlay only; do not delete them from the permanent chat history.
- Reconnecting or receiving a duplicate event must not reset an old message's lifetime indefinitely.
- Remove expired messages without causing the remaining messages to flicker or jump unnecessarily.
- Use stable message keys and predictable list updates.
- Avoid rendering expired messages again after a reconnect or screen refresh.
- Ensure the overlay remains readable without covering essential live controls or the main video.

Live chat consistency

- Display messages from spectators and authorized live controllers according to the existing access model.
- Ensure the same live session does not accidentally show stale messages from a previous stream.
- Associate each message with the correct live-session ID.
- Do not mix live-overlay messages with unrelated wedding chat messages.
- Ensure newly arriving messages appear promptly and older ones move upwards smoothly.
- Preserve any existing moderation, reporting, or privacy features.

Use the existing backend's real-time capabilities and reliable server timestamps or sequence identifiers where available. If the current transport cannot support the required reliability, identify the specific limitation and implement the smallest safe improvement supported by the current architecture.
