Fix Wedding Circle: Cross-Device Theme Persistence and Synchronization

Work directly on my existing The Wedding Circle project. Diagnose and permanently fix the bug where changing a wedding theme on one device does not appear on another device, even after refreshing the second device.

Current bug

- I change a wedding's theme on my phone.
- The desktop continues showing the old theme, even after a page refresh.
- The app may show a successful save even though the updated theme is not reaching the shared wedding record.
- The app has local state/local storage, server-side persistence, and Supabase PostgreSQL database routing. These must be investigated together.

1. Trace the complete theme data flow first

Inspect the existing code before making changes, particularly:

- "src/lib/wedding/store.ts"
- "pushCircle()"
- "startCircleSync()"
- "pullCircle()" and any equivalent remote-loading functions
- The wedding/circle API endpoints and server-side persistence layer
- Supabase database adapter, schema, and migration logic
- Theme selection controls, host/co-host permissions, revision/version logic, and local-storage cache
- Any real-time subscriptions or polling already implemented

Trace the complete path:

Theme selection → client state → save request → server → Supabase PostgreSQL → second device fetch/subscription → rendered theme.

Identify the actual root cause. Do not assume that adding a refresh, a timer, or a real-time subscription alone will fix the underlying persistence problem.

2. Make Supabase the shared source of truth

The active wedding's selected theme must be stored in its shared server-side wedding/circle record, using the existing schema and appropriate fields wherever possible.

Requirements:

- Persist the selected theme ID and any associated theme configuration required to reproduce the same appearance.
- Ensure the save request actually reaches the backend and writes to the active Supabase PostgreSQL database.
- Ensure the server returns a clear success or failure response.
- Do not show “saved” until the server confirms the write.
- If saving fails, preserve the user's selection locally as a pending change and show a clear retry state.
- Ensure desktop and mobile load the same persisted theme from the same wedding record.
- Do not rely on each device's independent "localStorage" value as the authoritative theme.
- Keep local caching for fast rendering if needed, but reconcile it with the server's confirmed version.

3. Implement reliable cross-device updates

Use the project's existing synchronization architecture where possible.

- When the host or an authorized co-host changes the theme, save it to the server and notify other connected devices.
- Prefer Supabase Realtime if the existing Supabase project, table configuration, and permissions support it safely.
- Otherwise, implement an appropriate authenticated server-side polling or revalidation fallback.
- When a device reconnects, opens the wedding, returns to the foreground, or refreshes, fetch and reconcile the latest persisted theme.
- Update the theme immediately on connected devices without requiring manual refresh.
- Subscribe only to the relevant wedding/circle, and clean up subscriptions when the user leaves it.
- Avoid duplicate subscriptions, repeated fetch loops, unnecessary database traffic, and memory leaks.

4. Fix conflict resolution and revision handling

Inspect the current revision, timestamp, version, and synchronization logic.

- A stale local revision must not overwrite a newer server-confirmed theme.
- A successful newer server update must not be discarded because the device has an older cached revision.
- Handle simultaneous changes deterministically, using server-confirmed versions or a reliable revision strategy.
- Ensure unrelated wedding updates do not accidentally overwrite the selected theme with an old value.
- Preserve all other wedding fields when saving a theme change.
- Prevent infinite save/pull loops and duplicate writes caused by synchronization events.

5. Preserve existing behavior and permissions

- Only the existing authorized host/co-host roles may change the shared wedding theme, according to the current permission model.
- Guests must receive the selected theme without gaining permission to modify it.
- Preserve all 23 existing themes, their colors, typography, decorative effects, and animations.
- Do not redesign the UI or change the theme-selection experience unless a minimal status indicator is required.
- Preserve the existing Supabase database configuration, migration/cutover state, developer access, authentication, chat, invitations, albums, live streaming, and wedding memberships.

- Do not create a second independent theme store or a parallel synchronization system if the existing architecture can be repaired.
