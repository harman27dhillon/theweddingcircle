The Wedding Circle — Firebase Validation Root-Cause Investigation & Permanent Fix

Objective

Firebase integration is still not validating correctly, despite updating the API key and confirming the Firebase project configuration.

Three problems need to be investigated together:

1. Firebase API key validation.
2. Firebase Project ID mismatch warning.
3. Email/Password authentication still reported as not enabled or not verified.

I suspect these errors may share an underlying implementation, configuration-loading, or validation problem.

Do not assume the displayed Project ID mismatch is genuine. Verify the actual request and response before accepting that diagnosis.

1. Trace the Complete Firebase Configuration

Inspect the actual current source code and trace every Firebase configuration value from storage to the validation request.

Expected environment variables:

- "FIREBASE_API_KEY"
- "FIREBASE_AUTH_DOMAIN"
- "FIREBASE_PROJECT_ID"
- "FIREBASE_APP_ID"
- "FIREBASE_MESSAGING_SENDER_ID"
- "FIREBASE_SERVICE_ACCOUNT_JSON"

Verify:

- Which exact variables are read by the frontend and backend.
- Whether the backend receives the latest saved values.
- Whether old configuration values remain cached.
- Whether multiple Firebase configuration objects exist.
- Whether a fallback or default configuration overrides the saved configuration.
- Whether the API key, Project ID, Auth Domain, App ID and service account all belong to the same project.
- Whether secret saving and retrieval are consistent.
- Whether blank values accidentally overwrite existing saved credentials.

Do not rename environment variables without checking every existing reference.

2. Investigate API Key Validation

The API key was updated from the older 30 October browser key to the newer 2 November browser key.

The newer key is accepted far enough to reach the next validation stage.

Investigate:

- The exact API endpoint being called.
- The HTTP status and response body.
- Whether the request uses the correct API key.
- Whether the response parser reads the correct project-identifying field.
- Whether the validation incorrectly treats an unavailable optional field as a mismatch.
- Whether the Firebase project ID is inferred from an incorrect API response.
- Whether API restrictions, Identity Toolkit API access or network errors are incorrectly classified.
- Whether a cached old API key is still being used.

Do not use a weak validation that merely searches for the project ID somewhere in the response.

Do not falsely reject a valid key.

4. Fix Email/Password Authentication Validation

Firebase Console already shows Email/Password authentication enabled.

However, Infrastructure still does not correctly confirm this.

Inspect the current implementation of:

"identitytoolkit.googleapis.com/admin/v2/projects/{projectId}/config"

Verify:

- The server uses the correct service-account credentials.
- The service account has the permissions required to read Firebase Authentication configuration.
- The OAuth access token is generated for the correct project.
- The request uses the correct authorization scope.
- The code reads the actual "signIn.email.enabled" value.
- Email Link is not confused with Email/Password.
- "passwordRequired" is interpreted correctly.
- HTTP 401 and 403 responses are treated as permission/authentication failures, not as disabled providers.
- A network failure is not reported as Email/Password being disabled.

If the endpoint or permission model is incorrect, fix it using the correct supported Firebase API.

Do not enable or disable providers automatically.
