PART 5 — Family Privacy and Selective Ceremony Access

Implement a proper privacy-control system allowing hosts and authorized co-hosts to control who can see posts, photos, videos, albums, ceremony details, and livestreams.

Add a Privacy & Family Access section inside the existing wedding settings.

5.1 Family membership

Support these family affiliations:

- Bride's Family
- Groom's Family
- Both Families / Shared Guest
- Unassigned

Allow the host or appropriately authorized co-hosts to assign or change a member's affiliation.

Do not automatically grant access to private content based only on family affiliation.

Unassigned members must remain unassigned until an authorized person assigns them. Their access must follow the wedding's existing default permissions.

5.2 Family visibility controls

Allow the host and authorized co-hosts to configure visibility for individual posts, photos, videos, albums, and ceremony updates.

Provide these audience options:

1. All Wedding Members
2. Bride's Family
3. Groom's Family
4. Selected People
5. Custom Guest Groups
6. Private Ceremony

Examples:

- A bride-side post can be hidden from the groom's family.
- A groom-side album can be restricted to groom-side guests.
- A bride-side ceremony can be shared with only selected elders from the groom's family.
- Selected members from both families can be permitted to see the same private content.

Make the selected audience visible to the content creator before publishing.

5.3 Private Ceremony mode

Add a Private Ceremony option when creating a ceremony, post, album, or livestream.

Authorized users should be able to:

- Enter the ceremony name.
- Choose eligible family groups.
- Select individual guests from either family.
- Exclude specific guests or groups.
- Choose whether comments are allowed.
- Configure access to associated photos, videos, and livestreams.
- Save and update the privacy settings.

Example: A Roka ceremony may be visible to the bride's family and selected elders from the groom's family, while remaining inaccessible to other groom-side guests.

Display a Private indicator only where appropriate. Do not expose restricted ceremony names, thumbnails, descriptions, or other details to unauthorized users.

5.4 Guest-level restrictions

Allow the host and authorized co-hosts to configure individual guest permissions without removing the guest from the wedding.

Supported controls should include:

- View shared wedding content.
- View bride-side content.
- View groom-side content.
- Access selected private ceremonies.
- Access selected albums and posts.
- Comment on selected content.
- Restrict access to specified content.

Permissions must be configurable per guest and per content item.

Ordinary guests must not be able to grant themselves additional access or override host restrictions.

5.5 Privacy selector when publishing

When creating a post, uploading media, creating an album, or starting a livestream, show a compact audience selector.

Options:

- All Wedding Members
- Bride's Family
- Groom's Family
- Selected People
- Private Ceremony

Show the selected audience before the user publishes or starts the stream.

Available options must depend on the user's role and permissions. Ordinary guests must not be allowed to publish into audiences they are not authorized to select.

5.6 Host and co-host controls

Only the host and appropriately authorized co-hosts may manage family access and private ceremony settings.

Allow authorized users to:

- Assign family affiliations.
- Approve selected guests for private ceremonies.
- Restrict or restore access.
- Update audience settings.
- Review the approved guest list for each private ceremony.

Preserve the existing host, co-host, and developer permission model. Do not give ordinary guests administrative privileges.

PART 6 — Private Livestream Access

Apply the family privacy system to Wedding Circle Live.

Before starting a livestream, the host or authorized co-host should be able to choose:

- Both families.
- Bride's family only.
- Groom's family only.
- Selected guests.
- An approved private ceremony audience.

Only authorized viewers may watch a restricted stream.

Requirements:

- Enforce viewer permissions on the server.
- Do not rely solely on hiding the video player or livestream card.
- Protect livestream access URLs and credentials.
- Prevent unauthorized viewers from joining through direct links or API requests.
- Apply access restrictions to comments and related media as well.
- Handle revoked access through server-side authorization and token expiry or invalidation where supported.

Keep the YouTube Live section separate and preserve its existing functionality. Do not claim that YouTube access is restricted by Wedding Circle unless that restriction is genuinely enforced by the YouTube configuration or the implemented integration.

If the existing streaming provider cannot support private viewer access, identify the limitation and implement the required compatible backend changes where possible.

PART 7 — Backend Security and Data Protection

Privacy is not complete if it is implemented only in the frontend.

Enforce permissions in the existing backend and database.

- Verify authorization before returning private posts, comments, albums, photos, videos, and ceremony information.
- Apply database security policies, such as Supabase Row Level Security or equivalent rules for the existing backend.
- Prevent unauthorized direct API access.
- Ensure search, feeds, notifications, and previews do not leak restricted content.
- Protect private media from publicly accessible storage URLs.
- Ensure access revocation prevents subsequent unauthorized requests.
- Avoid duplicating databases, user records, or permission systems.
- Reuse the existing authentication and data architecture whenever possible.
- Do not expose service-role credentials or privileged secrets in frontend code.

Explain any additional infrastructure required if the current backend or streaming provider cannot securely support a requested privacy feature.

Previously downloaded media and screenshots cannot be remotely erased from recipients' devices; do not claim otherwise.
