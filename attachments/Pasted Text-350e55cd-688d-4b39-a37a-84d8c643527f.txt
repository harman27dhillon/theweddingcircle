Wedding App Update — Feed Layout Fix + Two Independent Live Streaming Windows

Update the existing wedding app. Inspect the current code before making changes and reuse existing components, backend services, authentication, and design.

Critical requirements:

- Window A = native Wedding App Live.
- Window B = YouTube Live.
- Upload and Camera buttons must appear below the Feed text box.
- Preserve all existing data and functionality.
- Do not rebuild the app or introduce unrelated changes.

3. Function dropdown.

- Keep Upload and Camera on the same horizontal row.
- Place the upload-information (i) button immediately beside Camera.
- Preserve the Post button's existing behavior and permissions.
- Keep the function dropdown below the upload controls.
- Use compact spacing to save vertical space.
- Ensure the layout works on small Android screens without overlapping or horizontal scrolling.

2. Upload Button

- Rename the existing Gallery button to Upload, if it has not already been renamed.
- Tapping Upload must open the device's existing photo/video picker.
- Preserve existing upload validation and media-storage behavior.
- Support up to 50 photos and 5 videos per upload.

3. Camera Button

- Keep Camera immediately beside Upload on the same row.
- Tapping Camera must open the existing camera capture interface.

- Request camera permission only when required.

5. Side Colors Button

PART 2 — CREATE TWO INDEPENDENT LIVE STREAMING WINDOWS

The Live tab must contain two clearly separated cards:

1. Window A — Wedding App Live
2. Window B — YouTube Live

These are two different streaming systems. Do not reverse them, combine them, or make either dependent on the other.

PART 3 — WINDOW A: WEDDING APP LIVE

This is the app's own native live-streaming feature. The broadcaster streams directly from their device camera and microphone without requiring a YouTube URL.

1. Start Live and Request Permissions

- Display a prominent Start Live button.
- Only authorized hosts and co-hosts may start a broadcast, according to existing permissions.
- Opening the Live tab must not request camera or microphone access.
- When an authorized broadcaster taps Start Live, request camera and microphone access through the browser's native permission system.
- Request both permissions and handle each permission result correctly.
- If permissions are granted, initialize the camera and microphone and show a local preview.
- Display a Go Live button after the preview is ready.
- Do not start broadcasting until the broadcaster explicitly taps Go Live.

2. Camera and Microphone Controls

Before going live, provide:

- Camera preview.
- Microphone status indicator.
- Camera on/off control.
- Microphone mute/unmute control.
- Switch-camera option for front and rear cameras when supported.
- A Cancel button to exit the preview without broadcasting.

If permission is denied:

- Explain which permission is required.
- Provide instructions for enabling it in browser or device settings.
- Offer a retry option.
- Never falsely show that the stream has started.

If the camera or microphone is unavailable, already in use, or unsupported, show a clear error and allow retrying.

3. Go Live

When the broadcaster taps Go Live:

- Start a real live broadcast with video and audio.
- Make the stream viewable from other authorized wedding-circle devices.
- Display a clear LIVE indicator.
- Show the broadcaster's name and the selected wedding function, when applicable.
- Display the live video prominently.
- Show the current viewer count only when it can be measured accurately.
- Provide an obvious End Live button for the broadcaster.
- Handle weak networks and temporary disconnections gracefully.
- Update viewers' screens when the broadcaster disconnects or ends the stream.

Technical requirement: Implement real multi-user streaming, not a local camera preview that only the broadcaster can see.

Reuse existing streaming infrastructure if available. Otherwise, use a suitable WebRTC-based implementation with signaling and a compatible media-relay or streaming service.

If additional backend infrastructure is required, identify the setup required. Do not fake the streaming functionality or silently introduce an expensive paid service.

4. Live Comments

Add a real-time chat section beneath the native live video.

- Viewers can send text comments during the broadcast.
- Comments should appear promptly on all viewers' devices.
- Display the sender's name and message.
- Keep recent comments visible and allow users to scroll through them.
- Provide a clearly identifiable message input and Send button.
- Apply existing wedding-circle membership and moderation rules.
- Allow the host or authorized moderators to remove inappropriate comments.
- Prevent access to another wedding circle's live chat.
- Apply sensible message-length limits, validation, and rate limiting.
- Keep messages associated with the correct wedding and live session.
- Do not automatically turn live comments into permanent Feed posts.

Live chat should be temporary. Expire its data after the session according to the configured retention policy, without deleting unrelated wedding messages or posts.

5. Wedding-Themed Emoji Reactions

Add a compact reaction bar that works while viewers watch the native live stream.

Include:

- ❤️ Love
- 🥰 Adorable
- 💍 Wedding
- 🥳 Celebration
- 💃 Dance
- 🕺 Dance
- 🎉 Party
- 🌸 Blessings
- 🧿 Nazar protection
- 👏 Applause

Behavior

- Viewers can tap emojis to send reactions.
- Reactions appear to other viewers in real time.
- Use tasteful floating or popping animations over the video.
- Do not obstruct the video, comments, or important controls.
- Keep animations lightweight for mid-range Android devices.
- Apply rate limits to prevent reaction spam.
- Do not play sounds automatically.
- Do not store reactions as permanent wedding posts.

6. End Live and Release Resources

When the broadcaster taps End Live:

- End the actual broadcast.
- Stop camera and microphone media tracks immediately.
- Close the streaming connection and release camera/microphone resources.
- Update all viewers' screens to show that the stream has ended.
- Display an offline screen with an option to start another broadcast.
- Do not automatically record or save the stream.
- Do not upload the broadcast to the wedding album, Google Photos, Firebase Storage, or other permanent media storage.
- Clean up temporary streaming resources according to the existing backend architecture.

The native broadcast is a temporary live experience, not a recording feature.

PART 4 — WINDOW B: YOUTUBE LIVE

This window is exclusively for YouTube Live.

1. Attach YouTube Link

- Keep the existing YouTube URL input field.
- Keep the Attach button.
- Allow authorized hosts and co-hosts to attach a YouTube Live link.
- Validate the URL and reject unsupported links with a clear message.
- Persist the attached link using the existing wedding-event data model where possible.
- Do not request camera or microphone access to attach or watch YouTube.
- Do not require a native Wedding App Live session to attach a YouTube link.

2. YouTube Player

After a valid link is attached:

- Display the actual YouTube player inside Window B.
- Support standard YouTube watch URLs and supported YouTube Live URLs.
- Convert supported URLs into the appropriate safe embed format.
- Respect YouTube's playback and embedding restrictions.
- Display a clear message if the stream is offline, unavailable, private, or cannot be embedded.
- Allow guests to watch inside the wedding app when YouTube permits playback.
- Preserve the attached link when users navigate away and return.

Never falsely indicate that a YouTube stream is live when it is unavailable or offline.

3. Keep Both Windows Independent

- Attaching a YouTube link must not start Wedding App Live.
- Starting Wedding App Live must not require a YouTube link.
- Ending Wedding App Live must not stop or detach YouTube Live.
- Changing the YouTube URL must not interrupt the native broadcast.
- Keep each window's status, controls, and data separate.
- Do not share the native stream's camera permissions with the YouTube player.
