FIREBASE DIAGNOSTIC FIX — INSTRUCTIONS FOR GROK BUILD

Apply ONLY the source-code patch below to src/lib/developer/cloud.ts in this existing project. It is based on the updated source archive supplied on 3 November 2026. If the file differs, merge these two changes into interpretFirebaseProject(); do not overwrite unrelated work or apply the older broad fix package.

PRESERVE ALL EXISTING CREDENTIALS AND CONFIGURATION
- Do not change, delete, replace, regenerate or rotate any API key, service-account JSON, private key, token, password, signing secret or vault encryption key.
- Do not overwrite hosting environment variables or saved database/vault settings.
- Do not change Firebase project settings, API restrictions, authorized domains, IAM permissions, Authentication providers, DNS or Cloudflare settings.
- Do not clear the vault, re-save credential forms, run configuration reset commands or migrate data.
- Do not print credential values, request URLs containing keys, raw Google response bodies, or arbitrary provider metadata in logs or UI.

WHY THIS PATCH IS NEEDED
interpretFirebaseProject currently shortens Google's response to 240 characters through redactCloud(), THEN looks for restriction reasons. A reason appearing later is lost, leading to the misleading generic "Firebase rejected the web API key" message. This was reproduced using synthetic data, not production credentials.

WHAT TO CHANGE
1. Classify restrictions using the full response body, without displaying that body.
2. For HTTP 400/401/403, return only a recognized, allowlisted Google error code and a fixed safe explanation. Never echo arbitrary provider text. Existing successful-response/project matching logic and the needs_setup handling remain in place.

VALIDATE BEFORE PUBLISHING
- Add/run regression tests for a restriction reason appearing after character 240, API_KEY_SERVICE_BLOCKED, API_KEY_INVALID, generic PERMISSION_DENIED, malformed response JSON and HTTP 401.
- Confirm fake secrets placed in response metadata do not appear in returned diagnostic messages.
- Run the project's type check and build. Report failures rather than silently changing unrelated files.
- Publish the updated app through the normal Grok Build process. Do not change credentials as part of publishing. Normal existing build checks may run; this patch requires no new migration.
- After publishing, ask the owner to press Test connection again. Display the NEW check timestamp and diagnostic so an older stored error is not mistaken for a new response. Do not erase stored checks automatically.
- The current Firebase test performs more than the initial web-key request and may fall back to a synthetic password sign-in probe. Do not automatically run live provider tests merely to validate this code patch.

IMPORTANT LIMIT
This patch improves diagnosis. It does not guarantee that Firebase connectivity or email/password login works. If the next result identifies a genuine provider configuration problem, report it and wait for the owner's direction before changing account settings or credentials.
