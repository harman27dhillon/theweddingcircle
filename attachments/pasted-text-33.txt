The Wedding Circle — Complete Production-Readiness Audit and Upgrade

Act as a senior Android, React, backend, database, security, and production deployment engineer. Your task is to audit and upgrade my existing The Wedding Circle project to make it reliable, secure, performant, and ready for eventual Google Play Store production release.

1. Critical rules — protect the existing project

- Work on the existing project. Do not rebuild it from scratch.
- Preserve all working features, UI designs, animations, wedding themes, navigation, layouts, and user workflows.
- Do not remove features, simplify the design, replace working implementations with mockups, or introduce unnecessary dependencies.
- Do not overwrite or delete existing user data, wedding records, database tables, storage files, environment variables, or configuration.
- Preserve all nine existing wedding themes and ensure theme settings apply consistently throughout the wedding experience.
- Keep the existing Grok Build workflow functional so I can continue updating and testing the app there.
- Do not migrate databases, change hosting providers, rotate credentials, or make destructive infrastructure changes without explaining the reason and obtaining my approval.
- Never expose secrets, private keys, access tokens, service-role keys, or database credentials in frontend code, logs, or generated reports.
- Do not claim a test passed unless you actually ran it and verified its result.

2. Begin with a complete audit

Before making changes, inspect the actual project structure, dependencies, build configuration, Android wrapper, backend, database integration, authentication, storage, API endpoints, and deployment settings.

The project has used React, TypeScript, Vite, Tailwind CSS, Motion, Lucide React, an Express backend, and an Android wrapper. Verify the current implementation instead of assuming every technology or configuration remains unchanged.

Produce an audit covering:

- Critical errors and crash risks.
- Missing or incorrect production configuration.
- Security vulnerabilities and exposed credentials.
- Database persistence and synchronization risks.
- Broken or incomplete features.
- Performance and memory issues.
- Android build, signing, and compatibility issues.
- Missing privacy, permission, and error-handling safeguards.

Classify findings as Critical, High, Medium, or Low. Distinguish confirmed defects from items that require external credentials, device testing, or deployment access.

After the audit, fix verified problems incrementally, starting with Critical and High severity issues. Preserve a clear record of changes.

3. Production-grade Android build

Verify the Android project's actual build system and release configuration.

- Ensure a reproducible release build can be generated.
- Configure the correct application ID, version name, version code, minimum SDK, target SDK, and supported device configurations.
- Verify that the release AAB is generated through the proper Android Gradle signing workflow.
- Configure secure release signing using an upload keystore. Never commit the keystore, passwords, or private signing material to source control.
- Keep debug signing separate from release signing.
- Verify the resulting AAB's signature and build integrity using appropriate Android tooling.
- Check Android permissions and remove unnecessary permissions only when confirmed safe.
- Check app launch, splash screen, status bar, keyboard behavior, navigation, orientation, camera access, media access, and back-button behavior.
- Confirm that the app does not depend on a development server or development-only configuration.
- Confirm that production API URLs, HTTPS, and environment variables are correctly configured.
- Check compatibility with current Google Play requirements, including applicable target API requirements, using authoritative documentation where available.

Do not manually sign an AAB using an improvised procedure or claim that a bundle is production-ready merely because a signing command reports success.

4. Backend and database reliability

Inspect the actual backend and database used by the existing app.

- Verify that wedding information, user accounts, chat history, posts, albums, invitations, and other supported data persist correctly.
- Identify any data that is stored only in memory or localStorage and could disappear after a restart, reinstall, deployment, or device change.
- Do not silently replace existing persistence with a new database or storage service.
- Verify authentication, authorization, access policies, data validation, error handling, and safe synchronization.
- Ensure that hosts, co-hosts, family members, and ordinary guests can perform only their permitted actions.
- Prevent unauthorized reading or modification of another wedding's private information.
- Verify that production builds use the intended backend rather than development endpoints.
- Protect against duplicate submissions, failed requests, race conditions, and inconsistent updates.
- Check database migrations and backups where the existing provider supports them.
- Never log passwords, tokens, private messages, or sensitive personal information.

Do not claim database security or backup readiness without verifying the actual configuration and available permissions.

5. Security and privacy

Conduct a practical security review of both frontend and backend.

- Check for exposed API keys, secrets, database credentials, insecure endpoints, unsafe file uploads, and missing authorization checks.
- Verify that private wedding spaces and media cannot be accessed merely by guessing an identifier or URL.
- Verify upload type and size validation, rate limiting where appropriate, and protections against common web vulnerabilities.
- Validate inputs on the server, not just in the frontend.
- Use HTTPS for production communications.
- Avoid collecting unnecessary personal information.
- Verify privacy controls for posts, albums, wedding invitations, live sessions, and family access.
- Ensure host and co-host privileges cannot be acquired by manipulating client-side state.
- Review account deletion, data deletion, privacy disclosures, and applicable Google Play requirements.

Do not expose private data while testing or weaken security rules to make features appear functional.
