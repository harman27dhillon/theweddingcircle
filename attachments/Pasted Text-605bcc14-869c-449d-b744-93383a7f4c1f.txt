PHASE 1 — CAMERA ORIENTATION AND CAMERA SWITCHING
========================================================

CURRENT PROBLEM:

On an Android phone held upright in portrait orientation, the camera preview still appears sideways in the existing camera/live interface.

Captured photos or videos may also have incorrect orientation.

Front/rear camera switching has previously displayed an error indicating that the camera could not be switched and that the current camera remains on.

A. DIAGNOSE ORIENTATION

Inspect:
- Actual MediaStream video-track settings.
- Video source dimensions.
- Camera constraints.
- Device and screen orientation.
- Preview container dimensions.
- CSS transforms and object-fit behavior.
- Photo canvas dimensions and transformations.
- MediaRecorder output dimensions and orientation metadata.
- Any native camera or WebView bridges.

Determine the actual cause rather than guessing.

B. CORRECT PORTRAIT AND LANDSCAPE HANDLING

Requirements:
- When the phone is held vertically, the camera interface should appear upright in portrait mode.
- When the phone is rotated horizontally, respect landscape orientation where supported by the current application architecture.
- Keep the preview properly framed without stretching or distorting the image.
- Do not introduce an unnecessary rotation that breaks cameras whose source is already correctly oriented.
- Ensure the capture preview matches the resulting media.

C. CORRECT SAVED MEDIA

A correct-looking preview is not sufficient.

Verify the actual captured photo and recorded video.

Where required, correct:
- Photo canvas orientation.
- Output dimensions.
- Rotation metadata.
- Supported recording configuration.
- Playback interpretation.
- Uploaded and downloaded media orientation.

Do not assume that CSS rotation corrects the underlying file.

Use the most reliable method supported by the actual runtime. Avoid introducing a heavy media-processing dependency unless needed and justified.

D. CAMERA SWITCHING

- Prefer the rear camera initially where supported.
- Allow front/rear switching where supported.
- Release and replace tracks safely when required.
- Update the actual outgoing broadcast video source when switching during an active stream.
- Preserve the microphone stream when appropriate.
- Prevent duplicate camera streams.
- Recover gracefully if the new camera fails to initialize.
- Never report success unless the source actually changes.

Acceptance criteria:
The preview is upright, front/rear switching works where supported, and the saved or broadcast media is verified rather than judged only by its preview.

PHASE 3 — LIVE VIEW: FOUR EQUAL STREAM TILES
========================================================

CURRENT PROBLEM:

The Live section has displayed an oversized inactive video placeholder.

The required interface is a two-column, two-row grid containing four equal stream tiles.

REQUIRED LAYOUT:

+----------------+----------------+
|                |                |
|    STREAM 1    |    STREAM 2    |
|                |                |
+----------------+----------------+
|                |                |
|    STREAM 3    |    STREAM 4    |
|                |                |
+----------------+----------------+

LAYOUT REQUIREMENTS:

1. All four tiles must have identical dimensions and aspect ratios.
2. Use a small, consistent gap horizontally and vertically.
3. The entire grid should be visible on a typical mobile screen without creating an unnecessarily tall inactive placeholder.
4. Keep the overall inactive Live interface compact, following the earlier preference to reduce its excessive screen occupancy.
5. Do not shrink the tiles so much that they become unusable.
6. Use responsive sizing rather than arbitrary fixed pixel dimensions.
7. Prefer portrait-friendly video tiles.
8. Preserve the existing premium Wedding Circle theme.
9. Keep the Live heading and relevant controls usable.
10. On larger screens, adapt the layout sensibly.

EMPTY TILES:

Each inactive tile displays a centered plus (+) button.

When tapped, the plus button should use the existing authorized flow to add or start a stream.

ACTIVE TILES:

- Display the actual video for that stream.
- Show appropriate loading, connecting, reconnecting, and ended states.
- Allow a tile to be expanded for easier viewing where supported.
- Allow a return to the grid without unnecessarily resetting stream state.

FOUR-STREAM REQUIREMENT:

Support four independent streams only to the extent genuinely supported by the existing streaming architecture.

Each stream requires its own identity, broadcaster, state, and lifecycle.

Starting, stopping, or reconnecting one stream must not accidentally overwrite or terminate another.

Do not:
- Duplicate one source across several tiles.
- Display false LIVE indicators.
- Treat an empty tile as an active stream.
- Claim four-stream support because four boxes appear on screen.

If the existing provider cannot support four simultaneous streams, report the limitation and implement an honest UI that reflects actual capabilities.
